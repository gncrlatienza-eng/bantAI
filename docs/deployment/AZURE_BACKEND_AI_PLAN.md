## Decision

Use an **offline-first hybrid** architecture. Android must make the first SMS safety decision with a real, tested on-device model; Azure adds an optional second opinion, campaign intelligence, sync, and administration. The ~3 GB training checkpoint is **not** an APK asset. Host only a promoted, inference-ready XLM-R bundle in a private Python service. Do not confuse a compressed on-device XLM-R with a guarantee of identical accuracy: it needs its own evaluation.

```text
Android SMS receiver -> local inbox -> on-device classifier -> local alert
                                      | (durable, consented sync when online)
                                      v
                              public HTTPS NestJS API
                              |              |
                       private PostgreSQL   private FastAPI/XLM-R
                              |                    |
                       campaigns/reports     versioned model artifact
                              \___________ model/campaign reconciliation ___/
```

| Layer | Runs there | Initial hosting choice |
|---|---|---|
| Android | SMS receipt/storage, privacy masking, real local inference, immediate alert, durable sync queue, explicit local/cloud provenance | Bundle a validated ONNX model + tokenizer for fresh-install offline protection; a separate download is an opt-in product tradeoff because it needs one initial connection |
| Public backend | OTP/auth (mobile Semaphore; portal auth separately), ingest, user isolation, reports, campaigns, sync, policy, audit | Azure Container Apps, public HTTPS ingress, Consumption profile; start at 0.5 vCPU/1 GiB and measure |
| Private AI | Full XLM-R classification/embedding, campaign matching, deferred heavy explanation, model-version check | Separate Azure Container App, **internal ingress**, one model process initially; benchmark 4 vCPU/8 GiB Consumption as a *candidate*, not a promise |
| Database | Persistent application data and release/job metadata | Azure Database for PostgreSQL Flexible Server 16, private VNet access, private DNS, TLS, backups/PITR |
| Artifacts/operations | Immutable model bundles, image registry, secrets, telemetry | Private Azure Blob Storage, Azure Container Registry, Key Vault, Azure Monitor/Log Analytics; managed identities and least privilege |

One VNet-integrated Container Apps environment can host the public backend and internal AI app; PostgreSQL uses a separate delegated subnet. Internal AI ingress limits callers to the environment, **not** to the backend identity, so retain application-level authentication. Use private endpoints for storage/registry/vault where subscription, region and cost permit; otherwise treat public service endpoints protected by identity, TLS and firewall as a time-limited pilot exception, not equivalent isolation. Check the egress path for Semaphore and portal email before restricting outbound traffic. Start in **Southeast Asia** as a latency candidate for Philippine devices, subject to subscription/SKU availability and measured latency; record the actual data-residency decision.

Azure documents standard Container Apps Consumption at **up to 4 vCPU/8 GiB per replica**. Model file size is not RAM requirement: PyTorch loading, tokenizer, activations and concurrent requests can exceed it. If measured warm peak plus headroom does not fit 8 GiB, choose a 16 GiB Dedicated profile or a suitable 16 GiB VM after pricing; do not silently shrink or switch to a lower-quality model. Do not choose GPU, Azure ML endpoints or AKS before CPU benchmark, quota and cost evidence justify them. [Workload profiles](https://learn.microsoft.com/en-us/azure/container-apps/workload-profiles-overview), [internal ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-how-to), [private PostgreSQL networking](https://learn.microsoft.com/en-us/azure/postgresql/network/concepts-networking-private).

## What the checkout actually supports today

- `backend/Dockerfile` exists and `GET /api/health` plus `/api/health/ready` distinguish liveness from DB readiness. `docs/deployment/BACKEND_ROLLOUT.md` already covers one-time Prisma migrations and backend rollback. The local NestJS build and all 149 Jest tests passed on 2026-09-28. CI runs lint/tests/build, but has **no Azure release workflow**.
- `ai/Dockerfile` and `ai/requirements.inference.txt` now define a CPU-only, non-root, single-worker inference image. The Docker context excludes models and sensitive datasets. Direct dependencies are pinned; transitives still require a reproducible, hash-checked lock and image vulnerability scan before release.
- The FastAPI default serving path `ai/models/xlm-roberta-smishing` is absent here. The advisor-selected Model-C artifact at `ai/models/candidates/2026-09-21-colab-C` contains ~1.11 GB `model.safetensors` and ~17 MB `tokenizer.json`; local development configuration and a local-validation-only approval manifest point to C, and TestClient readiness/classification passed. **No hosted AI service is running.** `ai/models/VERSIONS.md` says ~3 GB `checkpoint-*` folders are for resuming training, not inference. Capture written approval provenance and complete serving/device/rollback gates before a production claim.
- FastAPI separates `/health` liveness from `/ready` readiness. `/ready` stays 503 until a separately controlled manifest matches exact artifact hashes and version and a real probe inference succeeds. Production additionally requires a production-scoped manifest with approval reference; the local-validation manifest cannot activate production. Production rejects a pickle checkpoint and loads only local safetensors. This is a serving safety check, **not** independent model-quality evidence.
- `backend/src/ai/ai.service.ts` times out classification at 3.5 s. Android now has a debug bundled **Model-C** INT8 XLM-R inference path and separate network-constrained sync worker; the receiver no longer waits for cloud classification. The Python Model-C FP32/INT8 conversion was compared on a reused historical holdout (not independent release evidence). A packaged tokenizer-plus-INT8 inference test passed on desktop, and Android debug build, JVM tests and lint passed. The APK includes C's manifest, but **no physical Android device inference or airplane-mode SMS test** has passed: the available emulator remained unauthorized to adb despite a safe restart attempt. The APK is ~383 MiB. AI scale-to-zero remains a measured pilot option, not a default production choice.
- The 2026-09-27 CPU-container candidate smoke measured a 16.53 s first call, far above the backend's 3.5 s deadline; a 0.063 s second call is encouraging but only one synthetic input on Docker Desktop. Keep the model warm before traffic and benchmark p50/p95/p99 on the actual Azure SKU and message mix before setting `minReplicas`, concurrency or timeouts.
- `backend/src/retraining/retraining.service.ts` now sends `x-api-key` to `/retrain`; the former service-key mismatch is resolved. AI retrain jobs remain in a local JSONL file, so Container Apps ephemeral storage or a second replica would lose/diverge those jobs. Backend retention and retraining use in-process cron; retraining has a DB advisory lock, but retention has no cross-replica coordination. Keep backend to one replica for the pilot until scheduled work is isolated/locked, and move retrain requests to a durable DB table or queue before scaling.
- `backend/src/sms/sms.service.ts` persists masked bodies and HMAC-pseudonymized senders, with `sourceId` idempotency. Preserve that contract; do not log message bodies, OTPs, tokens, model inputs, or unredacted URLs. `ai/service/routers/classify.py` deliberately keeps slow SHAP out of the synchronous path.
- Android replaces URLs/domains with `[URL]` before remote classification and sends domains separately to NestJS. FastAPI's `shares_domain` campaign path receives only the masked text; test campaign behavior explicitly and use the separate domain signal without sending raw SMS URLs to AI.

## Phased execution and exit gates

### Phase 0 — entitlement, budget, and model baseline (all owners)

1. Confirm the actual Azure subscription is **Azure for Students**, its remaining credit, allowed regions, Container Apps/VM quotas and service availability. GitHub Education eligibility does not prove an active credit balance; do not count GitHub and Azure's advertised $100 as two separate credits. Check costs in the Azure calculator for the chosen region, including warm AI hours, PostgreSQL, registry, Blob, Key Vault, networking, logs, backups and Semaphore.
2. Set spending alerts at multiple thresholds and an explicit pilot shutdown schedule. Azure budget alerts **notify but do not stop usage**. A 4 vCPU/8 GiB continuously running AI exceeds the monthly Container Apps free resource grants after roughly **12.5 hours** at full allocation before any other app uses them; actual idle billing and service costs need a region-specific estimate. Plan and fund 24/7 operation separately.
   **User-approved pilot ceiling: under $25/month.** Do not provision persistent PostgreSQL, private networking, registry and a warm full-model AI replica until a region/subscription-specific estimate shows the whole stack stays below that ceiling. A budget notification alone is not a hard spending cap. If the stack cannot fit, use a time-boxed demo environment with an explicit shutdown plan or request a higher budget; do not quietly remove privacy/security controls to hit the number.
3. Audit the actual model bundle: config, weights, tokenizer, label order, preprocessing, version metadata, hashes and license/data provenance. Benchmark warm/cold p50/p95/p99 classification latency, peak RSS, startup/download time and burst concurrency with the real bundle. Record acceptance thresholds *before* tuning. Reject an AI SKU if memory approaches its limit or the 3.5 s backend deadline is frequently missed.

Exit: subscription/budget decision, measured AI sizing, approved model identity and explicit UAT-versus-24/7 funding decision. [Azure for Students](https://azure.microsoft.com/en-us/free/students/), [Container Apps billing](https://learn.microsoft.com/en-us/azure/container-apps/billing), [budget alerts](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets).

### Phase 1 — make the applications deployable (Reymark + Maxene)

1. Complete the CPU-only, non-root, single-worker AI image with bounded inference concurrency; exclude training checkpoints, notebooks, datasets, dev tools and secrets. Its current direct dependency pins and local Docker build are **not** a scanned/hash-locked release. Build backend and AI images from reviewed commits, not a dirty local checkout. Store versioned model artifacts privately, fetch with a managed identity, verify SHA-256/signature metadata **before** loading, and pin the deployed model version to the image/revision. Compare a baked-in model image versus startup download only after timing both; a download on every cold start may defeat the latency target.
2. Implement honest AI readiness and fail closed on missing/corrupt/mismatched model in production. Keep liveness cheap. Use generous startup-probe timing for download + warm-up; never route traffic solely because `/health` returned 200. Make the NestJS AI timeout and cloud retries explicit; no retry storm on the SMS path.
3. Keep the corrected `/retrain` service-key forwarding covered by tests. Move the JSONL retrain queue to a durable backend table or managed queue with idempotency and completion state. Separate/coordinate cron retention and retrain triggering before allowing backend replicas >1. Keep training out of the serving container; trigger a reviewed training workflow, then validate and promote a new immutable artifact.
4. Reconcile Prisma migrations on a clean PostgreSQL 16 database, run `prisma migrate deploy` **once** as a controlled release job, and verify the mobile Semaphore OTP and portal email requirements in the current code. Do not ship `.env` files or secrets in images. Set exact `CORS_ORIGINS` and measured `TRUST_PROXY_HOPS`; disable external API docs in production.

Exit: both images build from clean source; production-config startup tests; a model hash/version mismatch prevents AI readiness; migration and OTP tests pass in staging; retrain enqueue survives restart.

### Phase 2 — secure Azure foundation and CI/CD (Reymark, reviewed by Gio)

1. Define staging and pilot/production as code (Bicep/Terraform): resource groups, VNet/subnets/DNS, Container Apps environment, backend, internal AI, private PostgreSQL, ACR, Blob, Key Vault, observability and cost tags. Separate staging and production secrets and data. For a credit-limited pilot, tear down staging when not in use; never reuse production SMS data in staging.
2. Backend: public HTTPS only, authentication/authorization, request limits, abuse protection, controlled CORS and narrowly configured proxy trust. AI: internal ingress only, HTTPS/service auth, request-size/concurrency limits and no external `/docs`. PostgreSQL: no public listener, TLS, least-privilege application role and restore-tested PITR. Grant managed identities only ACR pull, model-artifact read and named Key Vault secrets. Keep third-party credentials in Key Vault references.
3. Add GitHub Actions release workflow with **OIDC federation** to Azure, protected environment approval and least-privilege deploy identity. CI must lint/test/build, scan dependencies and images, emit a release manifest (Git SHA, image digest, model hash/version, migration set), deploy staging, run migration once, run smoke tests, then require Gio/team approval for pilot. No long-lived Azure service-principal password in GitHub.
4. Log status, correlation ID, model version, latency, error class and resource usage; redact content/identifiers. Alert on AI 503, model-version drift, backend 5xx, OTP failure, DB connection saturation, queue backlog, OOM, cold starts and budget thresholds. Set finite log retention.

Exit: IaC reproducible in a clean subscription; only backend is internet-reachable; secret/network/role review passes; automated staging deploy and rollback rehearsal pass. [Container Apps secrets](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets), [managed identities](https://learn.microsoft.com/en-us/azure/container-apps/managed-identity), [GitHub OIDC](https://learn.microsoft.com/en-us/azure/developer/github/connect-from-azure-openid-connect), [PostgreSQL backup/PITR](https://learn.microsoft.com/en-us/azure/postgresql/backup-restore/concepts-backup-restore).

### Phase 3 — restore the offline-first product contract (Gio + Maxene, before user rollout)

1. Evaluate Android-compatible representations of the **same approved XLM-R**: first export FP32 ONNX and check output/label parity against the approved PyTorch checkpoint, then establish a dynamic INT8 CPU baseline. Compare both against full precision on the same locked Filipino/English/Taglish holdout and real target phones, measuring Scam recall, Ham false positives, install size, RAM, latency and battery use. If INT8 accuracy drops, test selective or per-channel quantization and remeasure on those phones; if detection quality or device costs remain unacceptable, train a **distilled multilingual student from the approved teacher** and evaluate it under the same gates. Existing `ai/scripts/export_onnx_poc.py` and `ai/scripts/evaluate_onnx_holdout.py` are starting points, not completed Android validation. Do not call any candidate “same performance” until measured. Publish a signed/versioned model + tokenizer. **Bundle it for the offline-from-first-install promise.** A separate authenticated model download with atomic install can reduce APK size only if the team accepts and clearly discloses that offline AI starts *after* initial setup; it does not meet the fresh-install airplane-mode gate.
2. Move local inference outside the SMS broadcast deadline into reliable bounded work while storing/alerting immediately. Android must protect without an auth token or network; enqueue consented, masked, idempotent sync separately. The backend must never trust client-supplied `label` as a verified cloud result. Persist `ON_DEVICE`, `CLOUD_VERIFIED`, `CLOUD_ENRICHED` or `UNAVAILABLE` plus model version and timestamp; show later cloud corrections transparently.
3. Test fresh-install airplane mode, app cold start, actual SMS receive, local inference and persisted alert on a representative low-end Android phone. Measure install size, model RAM, p95 latency and battery. Test reconnection, duplicate/replayed sync, service outage and model rollback.

Exit: a genuine model verdict survives airplane mode with no backend; cloud outage never makes the app useless. [ONNX Runtime mobile guidance](https://onnxruntime.ai/docs/tutorials/mobile/).

### Phase 4 — limited UAT and promotion (all owners; Gio controls merge/release)

1. Deploy the promoted full model and NestJS to staging; run end-to-end device SMS tests with the public backend and internal AI, including OTP delivery, campaign/reports sync, unavailable AI, malformed payloads, rate limits and user-isolation checks. Verify that private AI/DB endpoints cannot be reached from the internet.
2. Set AI `minReplicas=1` during synchronous-path testing and demonstrations. After Phase 3 local-first asynchronous verification is in place, test whether AI can scale to zero between pilot sessions without compromising the user experience; 24/7 online verification requires a warm replica and funded capacity. Start with one backend and one AI replica, then load-test before scaling. If >8 GiB is required, switch to measured 16 GiB capacity rather than allowing OOM.
3. Rehearse database restore, image/model rollback and an AI-down day. Deploy immutable revisions; canary the backend and model under real readiness checks, then shift traffic. Roll back images/model pointers, not live database files. Use forward-compatible migrations; regenerate or version campaign embeddings/centroids when model space changes.
4. Release to a small consented test group only after security, offline and budget gates pass. Monitor latency and false negatives/false positives; promote more broadly only when the acceptance thresholds hold.

Exit: signed-off test evidence, cost runway, restore/rollback evidence and active monitoring. [Container Apps revisions](https://learn.microsoft.com/en-us/azure/container-apps/revisions), [health/startup probes](https://learn.microsoft.com/en-us/azure/container-apps/troubleshoot-container-start-failures).

## Decision boundaries / unresolved evidence

- **Use Model-C as the selected teacher, not the older checkpoint.** Advisor approval is reported, but production serving is not configured and release/device performance gates remain. Its current `candidate-` storage tag must not be mistaken for the deployed model version.
- **Do not claim production-ready offline AI today.** A real-model debug path exists, but physical-device, independent holdout, size/performance and signed-release gates are incomplete. The heuristic remains a clearly labeled unavailable-model safety net, not the release feature.
- **Do not claim the student credit funds continuous service.** Check the actual subscription and region-specific forecast. Pilot on-demand usage and 24/7 production are different budgets.
- **Do not expose AI, PostgreSQL, model Blob or credentials in the APK.** The app talks only to NestJS over HTTPS when online.
- This plan itself deploys no infrastructure and changes no WBS status. Update the existing backend rollout checklist and Gio-owned WBS/DEV_LOG as implementation is completed and reviewed.
