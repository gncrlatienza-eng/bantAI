## Implemented locally

- Portal identity uses nullable `User.webRole` with only `SHIELD` and `ADMIN`. Mobile-only users have no web role. Client-audience JWT routes remain deny-by-default and require Shield role, account status, membership, active license, capability and entitlement where applicable.
- The old Research/Organization/Tier subscription enum values are removed from the new Prisma schema. The migration backfills only verified established portal identities and explicitly stops if legacy `License` records exist, pending contract reconciliation. This prevents an automatic Research/Organization entitlement upgrade.
- Shield campaign reads and exports use an explicit published campaign serializer. The normal Shield campaign page has no message examples. AI-added domains reset publication for human review. Shield masked examples live in a separate table, require Admin approval, and are filtered again on read.
- The read-only Shield API has scoped campaign, indicator, timeline, masked-message and export endpoints. Tenant keys store a digest and show the secret once. Guard checks scope, creator role/status/current membership, organization status, license, quota and rate. Tenant and Admin usage views store only safe route/method/status metadata.
- Admin can create dormant unpublished campaign drafts; edit/publish intelligence; add or remove domain indicators; reactivate campaigns with matching evidence; archive campaigns without deleting their history; approve masked examples; inspect/revoke Shield keys; manage usage limits; and view global API activity and recent audit events. Indicator edits reset publication. Archival stops matching and withdraws Shield publication. Privileged campaign changes, masked approvals, report validation/rejection and restricted report reads create audit events.
- Shield and Admin navigation are separate. Shield has Overview, Campaigns, API, Exports, Notifications, Documentation and Account. The old client message/analytics routes redirect to safe Shield routes.
- Admin report and FP/FN screens now use the backend's `Pending`/`Validated`/`Rejected` values. A report can transition from Pending only once, so a second decision returns a conflict instead of replacing the original resolution or audit trail.
